Source here Failed Runs https://lucid.app/lucidchart/10f75867-1ef6-4aa1-85c1-91949e31e592/edit?page=0_0# General oc get anarchyrun -n anarchy-operator -l anarchy.gpte.redhat.com/runner = failed Looking at the runs: Each run is for an action . This is the point where it is going to tell Ansible Tower to go run the job for provision/destroy/other. Event column is empty. Usually you would see an event like ' completed '; this means that Tower has called back and said that it has completed its job and more ansible processing needs to run. Subject column. You can check if the failed runs are for different subjects. Checking provisioning failures: Go to babylon-ui. Click on AnarchyRuns and wait for it to load. Search for of the provisioning failures and click on the name. This will pull the log output from Tower. Check the failed message. Here is important to evaluate if the error is before, during or after the provisioning. This is important since it will help decide if it's secure to clean the failed run or cleaning needs to happen beforehand. Before provisioning Tower found and error and it was not able to run the provision request. We know there are no cloud resources associated with the Subject. It is safe to purge not only the run but the whole Subject as long as the ResourceClaim is cleaned. NOTE: Babylon-admin-ui currently does not provide a button to delete the Subject From the babylon-ui, go back to the run and click the AnarchySubject column (5th column). Check if the resourceClaim exist. Check the definition to see if there is a deletionTimestamp. This indicates that deletion has started. This happens when the ResourceClaim is deleted. Check the runs for the subject and look for *delete* in the name column. Usually it will be in a queued state, since it's waiting for the provision to finish. The delete won't move on unless it succeeds on previous runs. If you delete the failed provisioning run it will trigger the delete to finish. About finalizers: As long as there are finalizers there is something for anarchy to do. Since there is nothing provisioned and there is no resourceClaim, instead you could delete the finalizers. Copy the subject name from the UI oc edit anarchysubject -n anarchy-operator ${SubjectName} Delete the finalizers block, save and exit. Everything will be gone oc get anarchyrun -n anarchy-operator -l anarchy.gpte.redhat.com/runner=failed Examples of possible failures: Have to evaluate from the Tower log output. Usually it will need an patch in AgnosticV and so on. Incorrect git referense Incorrect path Incorrect virtualenv Checking deletion failures: This would usually imply that at least Tower tried to deploy something. Go to the babylon-ui and go the AnarchySubject. Get the provisioning Tower Job ID either from the top of the page or from the definition (usually at the bottom). Login to Tower using credentials from bitwarden and check the Job id. Evaluate if something was provsioned or not and what caused the error. If there are no resources and resourceClaim then you can delete finalizers. Failed Subjects oc get anarchysubject -n anarchy-operator | grep failed Failed provision When you run the above command: The last column will indicate if there was a deletion attempt. If it's empty it would mean that no delete of the environment has been run. Delete is something that either the user or admin can requiest from CF or the automated process that cleans failed environments. This could also indicate that currently the developer is troubleshooting the failure and it may not be necessary to delete the environment. To check this, you would. oc edit ${ Subject } From the top of the file: Check the username (resource-claim-namespace) , is he a developer? Get the CF guid (resource-claim-name) , end of line. Check CF for that GUID, check the log file on admin host. From the bottom: Check the towerJobs block. Failed destroy Edit the Subject. Scroll to the bottom and review the towerJobs block. Each step should have deployerJob , startTimestamp and completeTimestamp *Check any job that does not have those. (if sandbox check below) If the environment is sandboxed: First check if the sandbox has been released. Get sandbox id from Subject. From the admin host use sandbox-list --all | grep sandboxID If the sandbox appears in-use , evaluate if its the same provision you are looking or if it has been reprovisioned. You can decide based on the user and time of creation info. If the sandbox has been released, delete finalizers .
