Finding Failed Destroys Failed destroy on an environment within Babylon is indicated by an AnarchySubject with a .metadata.deletionTimestamp that is some time in the past. A simple report on failed destroy can be pulled with `oc`: $ oc get anarchysubject -o jsonpath='{range .items[?(@.metadata.deletionTimestamp)]}{.metadata.name}{"\n"} {.metadata.deletionTimestamp}{"\t"}{.spec.vars.current_state}{"\n"}{end}' -n anarchy-operator rhtr-azure.acm-man-1.dev-xqdqs 2020-10-01T08:43:12Z destroying rhtr-openstack.ocp4-knilab.test-7rdpb 2020-10-02T03:03:58Z provision-failed rhtr-openstack.red-hat-remediation-lab.test-mq8ck 2020-10-06T23:04:19Z started Note the importance of the spec.vars.current_state : - destroying - Ansible Tower job has been started, but this job has likely failed. - provision-failed - Failed on initial provision, destroy processing has not started. - started - Provisioned, but for some reason destroy processing has not started. Environments that have already attempted a destroy may be found by label, but note that this may not show everything, particularly if for some reason the initial destroy was not processed. oc get anarchysubject -n anarchy-operator -l state=destroying Extracting Claim Information from AnarchySubject A deletion request is initiated by deleting the ResourceClaim that represents the initial request. This means that the normal way of fetching the CloudForms GUID and requesting user is not available. This information is still preserved in the annotations of the AnarchySubeject. To retrieve the ResourceClaim namespace and name: oc get anarchysubject -n anarchy-operator -o custom-columns='NAMESPACE:.metadata.annotations.poolboy\.gpte\.redhat\.com/resource-claim-namespace,NAME:.metadata.annotations.poolboy\.gpte\.redhat\.com/resource-claim-name' <SUBJECT NAME> For example: $ oc get anarchysubject -n anarchy-operator rhtr-sandboxes.acm-hub.dev-vlq8f -o custom-columns='NAMESPACE:.metadata.annotations.poolboy\.gpte\.redhat\.com/resource-claim-namespace,NAME:.metadata.annotations.poolboy\.gpte\.redhat\.com/resource-claim-name' NAMESPACE NAME user-jsnow-redhat-com rhtr-sandboxes.acm-hub.dev-3962 Checking for Failure in Anarchy Processing If the value of spec.vars.current_state is anything other than destroying then this indicates some sort of failure of Anarchy processing has occurred for this catalog item. Failure of Anarchy processing will prevent the destroy from initiating and so these issues must be resolved first. $ oc get anarchyrun -n anarchy-operator -l anarchy.gpte.redhat.com/subject=rhtr-sandboxes.acm-hub.dev-qnl5r NAME GOVERNOR SUBJECT ACTION EVENT RUNNER AGE rhtr-sandboxes.acm-hub.dev-qnl5r-destroy-mmfbr-xn2qq rhtr-sandboxes.acm-hub.dev rhtr-sandboxes.acm-hub.dev-qnl5r rhtr-sandboxes.acm-hub.dev-qnl5r-destroy-mmfbr failed 9d Once a failed AnarchyRun is identified, details can be found in the AnarchyRun's spec.result.ansibleRun . For example: $ oc get anarchyrun rhtr-sandboxes.acm-hub.dev-qnl5r-destroy-mmfbr-xn2qq -n anarchy-operator -o yaml | yq eval spec.result.ansibleRun - | tail -n 11 - action: uri end: "2020-10-07T20:15:00.611049Z" hosts: localhost: failed: true result: _ansible_no_log: null msg: dict2items requires a dictionary, got <class 'ansible.template.AnsibleUndefined'> instead. id: 0a580a83-00b7-4782-692c-0000000000eb name: 'babylon_anarchy_governor : Cancel provision tower jobs' start: "2020-10-07T20:15:00.596082Z" Any failure of this sort indicates a bug in Anarchy or the Ansible that Anarchy was executing. In this case the error pointed to a problem in the babylon_anarchy_governor , leading to a Pull Request to fix the issue. Finding Ansible Tower Jobs Once an AnarchySubject with a failed destroy has been identified the next step is to investigate the provision and destroy tower jobs. The tower jobs can be listed with: $ oc get anarchysubject rhtr-openstack.ocp4-knilab.dev-wnpsp -n anarchy-operator -o yaml | yq eval .status.towerJobs - destroy: deployerJob: "54065" provision: completeTimestamp: "2020-10-08T00:18:42Z" deployerJob: "53691" The provision tower jobs need to be checked to see if any cloud resources were created for the provision. If the logs of the tower job indicate that the failure occurred before anything was provisioned, or if no provision deployerJob is listed, then the AnarchySubject may be force-deleted as described below. The jobs can be found by id in the production tower job list . Jobs may be found by id using id:<JOB_ID> .
