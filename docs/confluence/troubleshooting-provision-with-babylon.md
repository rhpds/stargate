This content assumes you have Babylon command line access . Troubleshooting Provision with Babylon This guide provides troubleshooting procedures for Babylon's provisioning. Understanding Babylon Architecture Babylon is a multi-cloud infrastructure management system that orchestrates the lifecycle of lab and demo environments. The core components are: : Ansible deployment framework that handles actual infrastructure provisioning AgnosticV : Catalog management system for available lab configurations : Manages catalog resources in OpenShift : OpenShift operator that manages resource pools via ResourceClaim/ResourceHandle Anarchy : Kubernetes operator for stateless API operations and workflow orchestration (Ansible Automation Platform) : Executes Ansible jobs via Tower for AnarchyRuns Key Resource Flow User Request : User creates a ResourceClaim in their namespace Poolboy Matching : Poolboy matches the claim to a ResourceHandle (format: guid-{XXXXX} ) Anarchy Orchestration : ResourceHandle maps to an AnarchySubject representing the environment AAP2 Execution : AnarchySubject triggers AnarchyRuns (mostly via AnarchyAction CR's) that execute as AAP2 jobs Deployment : AAP2 runs AgnosticD playbooks to provision resources, which makes a callback to the AnarchySubject to update status If a deployment doesn't report back in-time, Babylon requests direct job status information from AAP2 Working with GUIDs Every Babylon-managed environment has a unique GUID that serves as the primary identifier across all systems. GUID Structure Full GUID : Appears in ResourceClaim metadata (e.g., xqw8w or xqw8w-N for Binder items) ResourceHandle : Maps to GUID as guid-{5char} (e.g., guid-xqw8w ) AnarchySubject : Named with catalog and GUID (e.g., sandboxes-gpte.ocp-wksp.prod-znxvx ) Finding when something changed in a resource Replik8s holds the backup on the other cluster from the prod host.
